# Plan-Then-Delegate

## 核心原则

主代理只做两件事：**和用户对齐方案** + **整理文档**。具体代码改动通过插件内置 agent 落实，**串行、前台**。

主代理**不**：
- 给子代理的落实细节提意见
- 自己接手问题和下场写代码改文件（除非用户明确要求"这次你直接改"）
- 自己看子代理处理问题后的 log（应该把用户反馈的 log 文件路径直接丢给子代理让它自己看）
- 用 `run_in_background=true` 起做写操作的子代理
- 把同一个问题拆给多个子代理
- 让子代理来写文档
- 自己跑编译 / 测试验证（编译归 F，测试归 V；主代理不关心命令、不重复跑）

## 工作流

整体阶段：

1. **方案对齐**（第 1 节）：主代理排查根因，与用户确认方案
2. **分发子代理**（第 2 节）：串行前台调起 impl-agent
3. **收集反馈**（第 3 节）：主代理对每个子代理返回做轻量校验
4. **补充测试循环**（第 4 节，可选）：所有 F 完成后，主代理询问用户；同意则进入 test-agent ↔ impl-agent 循环
5. **统一整理文档**（第 5 节）：主代理整合改动到项目文档；不跑编译

### 1. 排查与方案对齐

主代理通过 Read / Grep / Glob / 必要的 WebSearch 等只读工具排查根因，把"根因 + 拟定方案"呈现给用户，**等用户明确确认**后再分发。

不确定的点不要替用户拍板。

### 2. 分发子代理

一次只起一个 impl-agent，前台运行，等返回后再起下一个。**Agent 调用时必须传以下参数**：

- `subagent_type: plan-then-delegate:impl-agent`
- `name`：如 `F1`/`F2`，记录 name ↔ agent_id 供后续 SendMessage 续接

**prompt 模板**（必填字段不可省）：

```
## 任务背景  [必填]
<一句话说明问题>

## 根因  [必填]
<主代理已排查的根因>

## 已确认方案  [必填]
- 改动文件：<file_path>
- 关键代码 / 函数：<片段或定义>
- 命名 / 风格：<用户特别强调的偏好>

## 特殊编译命令  [可选]
<覆盖默认；通常不填>
```

需要返工时，用 SendMessage 续接同一 agent_id；若 SendMessage 不可用则冷启动新 agent 接力。

一个问题对应一个 impl-agent。同一问题涉及多个文件 / 多步，全部在同一个 agent 里完成。

### 3. 收集反馈并继续

子代理返回后，主代理只做轻量校验（看反馈里有没有偏离方案、有没有遗留点）。**不**重新读子代理改过的文件来"验证"——子代理 Edit/Write 失败会直接报错。

如果反馈正常，继续下一个；否则澄清问题，让子代理返工。

### 4. 补充测试循环（可选）

**触发条件**：所有 F 完成报告后，**且主代理工具列表中存在 `SendMessage` 工具**。主代理主动询问用户："是否要进行补充测试？" 用户同意才进入。

**核心结构**：每个 F 配一个 V（一一对应、严格串行，任何时候只有一对在跑）。主代理冷启动 test-agent 时传入 F 的 agent_id，之后 F ↔ V 通过 SendMessage 直连。主代理不参与中继，只等 V 的最终报告。

**详细执行规则**：见 [`references/test-loop.md`](references/test-loop.md)。

### 5. 统一整理文档

所有子代理（含可选的测试循环）都跑完后，主代理询问用户是否整合文档。文档结构由项目 CLAUDE.md / 既有文档惯例决定；不重复跑编译 / 测试。

## 何时不用本技能

- 单个简单改动（一行 typo、一个变量重命名）：主代理直接改更快
- 用户明确说"这次你直接改"
- 纯研究 / 探索任务（没有代码改动）
